# Autentikasi & Scope

API memakai **bearer token**. Belum ada OAuth2 — setiap permintaan membawa API key yang dibuat
untuk sebuah organisasi.

## Mengirim token

Dua header diterima, pilih salah satu:

```bash
# Cara utama
curl -H "Authorization: Bearer sk_api_..." https://sahabatkreator.com/v1/ping

# Alternatif, untuk alat yang tidak nyaman mengubah header Authorization
curl -H "X-API-Key: sk_api_..." https://sahabatkreator.com/v1/ping
```

<Callout variant="warning" title="Prefix token">
  Token baru memakai prefix `sk_api_`. Token lama ber-prefix `sk_live_` **masih berfungsi** (server
  menerima keduanya), tapi prefix itu sengaja ditinggalkan: formatnya identik dengan Stripe live
  secret key, sehingga GitHub secret scanning menandainya sebagai kebocoran dan menolak push.

  Kalau masih memakai token `sk_live_`, rotasi kapan saja lewat **Settings → API**.
</Callout>

## Key terikat ke organisasi, bukan pengguna

Ini penting untuk integrasi yang dipasang di banyak klien:

- Key mewakili organisasi tempat ia dibuat. Semua data yang diakses terbatas pada organisasi itu.
- Peran pembuat key di-resolve **setiap request**. Kalau pembuat key dikeluarkan dari organisasi,
  key **langsung mati** — tidak perlu dicabut manual.
- Satu akun sosial hanya boleh dimiliki satu organisasi. Mencoba menghubungkan akun yang sudah
  terhubung di organisasi lain menghasilkan `409`.

## Scope

Scope ditentukan **saat key dibuat** dan tidak bisa diubah setelahnya. Polanya
`<resource>:<read|write>`.

| Resource | Scope |
|---|---|
| `accounts` | `accounts:read`, `accounts:write` |
| `posts` | `posts:read`, `posts:write` |
| `analytics` | `analytics:read` |
| `reports` | `reports:read` |
| `media` | `media:read`, `media:write` |
| `renders` | `renders:read`, `renders:write` |
| `automation` | `automation:read`, `automation:write` |
| `ai` | `ai:read`, `ai:write` |
| `webhooks` | `webhooks:read` |

Scope hanya membatasi **key**. Di atasnya masih ada gate paket:

- `api_access` (Pro+) — diperlukan oleh semua endpoint `/v1`.
- `api_write` (Bisnis+) — diperlukan oleh method tulis.

Jadi key dengan scope `posts:write` di organisasi paket Pro tetap ditolak `402` saat mencoba
membuat post. Scope adalah izin key; paket adalah izin organisasi.

<Callout variant="info" title="Kenapa beberapa GET butuh scope tulis?">
  Endpoint `GET /v1/accounts/{platform}/authorize` dan `GET /v1/accounts/pending/{id}` memakai
  `accounts:write`. Keduanya bagian dari alur menulis (dan `pending/{id}` memuat aset yang belum jadi
  akun). Pola yang sama berlaku untuk polling render: `GET /v1/carousel/{id}` butuh `renders:write`,
  karena polling adalah bagian tak terpisahkan dari alur tulis — buat job lalu poll sampai selesai.
  Dengan begitu tidak ada konfigurasi key yang jadi setengah jalan.
</Callout>

## Batas key

| Batas | Nilai |
|---|---|
| Key aktif per organisasi | 10 (yang dicabut atau kedaluwarsa tidak dihitung) |
| Masa berlaku key | opsional, 1–3.650 hari saat dibuat |
| Rate limit | 60 permintaan / menit **per key** (bukan per IP) |

## Rotasi key tanpa downtime

1. Buat key baru dengan scope yang sama, di developer app yang sama.
2. Pasang key baru di integrasi Anda, biarkan key lama tetap aktif.
3. Pastikan tidak ada lagi permintaan yang memakai key lama — cek kolom *terakhir dipakai* di
   **Settings → API**.
4. Cabut key lama.

Key yang dicabut langsung berhenti berlaku; permintaan berikutnya mendapat `401`.

## Menjaga token tetap aman

- Simpan di secret manager atau environment variable, jangan di kode.
- Jangan kirim token dari browser. Panggil API dari server Anda sendiri.
- Beri key terpisah untuk setiap integrasi supaya bisa dicabut satuan tanpa mengganggu yang lain.
- Kalau token pernah muncul di log, tangkapan layar, atau repo — cabut dan buat baru. Tidak ada
  cara memulihkan token; server hanya menyimpan hash-nya.
